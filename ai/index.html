Standards-grounded TEKS tutor retrievalLive

Ask about a Texas K–5 standard in any of ten subjects and get the matching standard with its citation, or a clear “not found.” It uses BM25 keyword retrieval over 2,259 TEKS records and an answer-or-decline rule. It makes no model call and logs nothing you type.

What it demonstrates

  • Grounding every answer in a primary source I can cite.
  • Declining instead of guessing.
  • Shipping retrieval as a small serverless function with no stored data.

Known limit: keyword matching can answer off-topic trivia that overlaps a standard’s wording, such as a question about a state capital. The evaluation method and results are in the public repository.

Grade 2 math tutor loop (Claude adapter built)Prototype

A tutor loop in which the answer key never enters the model’s context. Grading, hints and mastery run on the server, and the model works through four tools: get_question, submit_answer, get_hint and flag_for_teacher.

What it demonstrates

  • Guardrails: an output leak guard blocks the key whether it appears as digits, words, a letter or elimination language.
  • Cost control: per-student and daily cost caps, with a rule-based fallback when a cap is reached.
  • Privacy: pseudonymous ids, no free text stored, and RLS-protected pilot analytics.
  • Red-teaming: an attack taxonomy of 12 answer-extraction attacks and a 15-case harness.
  • Teacher control: tutor work is not graded unless the teacher turns that on.

Status: the Anthropic SDK and Vertex AI adapters are built but not yet run against a live model. The harness results come from a mock model, so they test the guards and the loop, not a model’s behavior.

Quality gates and lesson publisherLive

Five CI gates that fail the build, including automated axe-core accessibility scans and a question-quality validator. The validator checks for duplicates, “none of the above,” and longest-answer and answer-slot skew. About 380 Netlify function tests plus 35 learner-side test files cover the code.

How I work

Process, setbacks and what I changed

  1. Frame the problemwith teachers, parents and learners
  2. Set constraints firstprivacy, cost, accuracy, review
  3. Write the standard firstrules, then automatic checks
  4. Ship thin, then measuregolden questions, held-out test
  5. Break it on purposeoff-topic, messy input, edge cases
  6. Harden and documentwrite down what is unfinished
What went wrong, and how I fixed it (6 short notes)
Standards tutor · evaluationIt answered everything, including off-topic questions

What happened: keyword search always returns something, so the first version gave a confident wrong answer to off-topic questions.

What I changed: I wrote off-topic questions, tuned a decline rule on part of them and tested it on questions it had never seen. When the first rule fell short, I added a second signal: how many of the question’s words exist anywhere in the standards.

Then it got harder: when I loaded all ten subjects, some trivia matched a standard that mentions the same words. I recorded that as a known failure instead of removing it from the tests.

Takeaway: a threshold that looks fine on the data it was tuned on can fail on new questions, and again when the corpus grows. Hold some back and re-measure.

Standards tutor · source dataI would not build on a paraphrase

What happened: automated lookups of the Texas standards were blocked or returned summaries, not the exact wording.

What I changed: I used the official PDF, fixed line-break artifacts in the parse and locked the record counts into a regression test. Every answer cites the rule and notes that the state publishes it for information only.

Takeaway: ground the system in the primary source, and test the data pipeline, not just the model.

Standards tutor · architectureWhere to host it: price versus the visitor’s first impression

What happened: I compared three hosts using their own pricing pages. One has no free tier, one gives a small monthly credit, and the free one sleeps when idle, so the next visitor waits.

What I changed: I ported the retrieval to TypeScript and ran it as a function on the site’s existing host, then checked that it returned the same answers as the Python original.

Takeaway: choose the architecture by what the user experiences and what you already own, then prove the port is equivalent.

Style Studio · product qualityHairstyles that looked fake, shirts that showed skin

What happened: in preview testing, layers were mixed up and the hairstyle overlays looked artificial.

What I changed: I fixed the layering and coverage problems one round at a time through preview deploys, and parked the hairstyles until proper hair art exists.

Takeaway: cutting a feature is a design decision. A preview build lets a person review before anything goes live.

Assessment content · guardrailsGood-looking quiz questions with hidden patterns

What happened: a review of library quizzes showed patterns students learn to game, such as the right answer being the longest choice.

What I changed: I wrote the reviewer’s rules down, then turned them into a validator that fails the site build.

Takeaway: a rule that depends on someone remembering it will be skipped. Automated checks catch patterns, and a person still reads for meaning.

Parent reports · reliability“Every Friday at 5” changes twice a year

What happened: scheduled jobs run on universal time, so a fixed schedule drifts by an hour when the clocks change.

What I changed: the job runs at both possible hours and sends only the run that lands on 5 p.m. Central. It records the week it sent, so a retry cannot email a family twice.

Takeaway: design automation so that running it twice is harmless.
